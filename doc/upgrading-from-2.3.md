# Upgrading from 2.3 to 3.1

XeWe LED OS 3.1 is the 2.3.0 firmware rebuilt on XeWe OS 3.1. The LED engine (46 chipsets, six colour
orders, seven modes, the first-boot wizard and the 30 `$led` commands) and the LED web page were moved
into the `led` and `led-web` modules of xewe-os-modules. Home Assistant, HomeKit, Alexa and the
schedule page are modules of this repository (`src/`); the web catch-all is part of the
`web-interface` module. The aim was the same behaviour
as 2.3.0. This page lists every difference you can see.

## Before you flash

- **Settings are not carried over.** 3.1 does not read the 2.3 NVS layout, and the released image
  is a 4 MB merged image written from 0x0 whose NVS area is blank, so flashing it erases the stored
  settings (`./run.sh` erases the whole flash as well). After the upgrade the device runs the full
  first-boot setup again: device name, LED wizard, Wi-Fi, time zone, buttons and each smart-home
  module. Write down your Wi-Fi, LED settings, buttons and schedules first (`$led status`,
  `$buttons status`, `$system status`).
- Pair HomeKit again, run Alexa discovery again and provision Home Assistant again (the HACS
  integration finds the device once more; topics and unique ids are unchanged, so existing entities
  are reused).
- Stored button and schedule command strings keep working: every `$led` command keeps its 2.3.0
  name, arguments and response text.

## Web flasher and release files

**Release images are GitHub Release assets.** Nothing under `static/firmware/releases/` is
committed any more (2.x committed every image to the repository). Each release of
`xewe-labs/xewe-led-os` carries all 43 images of `release_matrix.csv` (c3 7, c6 14, s3 22) as flat
files:

```
https://github.com/xewe-labs/xewe-led-os/releases/download/<version>/<asset>
https://github.com/xewe-labs/xewe-led-os/releases/latest/download/firmware_map.csv
```

For example `…/releases/download/3.1.0/c6_20_19_3.1.0-c6-xewe-led-os.bin`. Per image there are three
assets named after the row's folders joined by `_`: the bin `<chip>_<data>_<clock>_<version>-<chip>-xewe-led-os.bin`
(a 4 MB merged image written at 0x0), `<chip>_<data>_<clock>_meta.json` and
`<chip>_<data>_<clock>_manifest.json` (an ESP Web Tools manifest whose part path is the bin's
asset name, so it resolves inside the same release). Each release also has `firmware_map.csv`,
`firmware-<version>.tar.gz` (the 2.2.x folder layout `<chip>/<data>/<clock>/`, for a flasher that
unpacks it) and `release_card.md` (the test record of that release). The 2.x images are re-hosted
as GitHub Releases of the same repository, tagged with their bare version (`1.0.1` … `2.2.2`),
marked legacy and not re-tested; none of them is ever "latest". The `latest/download` URL therefore
always names the newest 3.x release. The README ("Install a release") has the full key list.

What a 2.2.x flasher must change:

| | 2.2.x | 3.1 |
|---|---|---|
| where the images are | `static/firmware/releases/<v>/<chip>/<data>/<clock>/` in the repository | release assets (above); the same folders inside `firmware-<v>.tar.gz` |
| `firmware_map.csv` | `CHIP,LED_PIN_DATA,LED_PIN_CLOCK` | `CHIP,XEWE_MODULE_LED_PIN_DATA,XEWE_MODULE_LED_PIN_CLOCK,_PATH,_ASSET,_SIZE,_SHA256,_META,_MANIFEST,_BUILD_NOTES` |
| pins in `meta.json` | `config.LED_PIN_DATA`, `config.LED_PIN_CLOCK` | `config.XEWE_MODULE_LED_PIN_DATA`, `config.XEWE_MODULE_LED_PIN_CLOCK` |
| artifact paths | `path_rel_*` and `path_abs_*` | `path_rel_*` only, plus `artifacts.size`, `sha256`, `asset_name`, `meta_asset`, `manifest_asset` |

A flasher reads `firmware_map.csv`, picks the row for the chip and pins, and fetches its `_ASSET`
(or `_MANIFEST`) from the same release; `_SIZE` and `_SHA256` check the download. The columns that
start with `_` come after the pin columns, so a reader that takes the first three keeps working.
The 43 pin rows are the 2.3.0 rows; only the column names changed. Release download URLs answer
with a redirect that may lack CORS headers, so a browser flasher on another site has to be checked
against them before it relies on a direct fetch.

Building from source: `./setup.sh` and `xewe build` replace `build/scripts/*.sh`. Arduino IDE builds
are not supported (the modules are generated by setup).

## Flash layout (partition scheme)

- **3.1 uses the esp32 `huge_app` partition scheme** on all three chips (`[build] partition_scheme =
  "huge_app"` in `xewe.toml`): a 3 MB app partition (3,145,728 B) instead of 2.3.0's 2 MB `no_ota`
  one. With every integration the image is about 2.1 MB, which no longer fits 2 MB on c6. Neither
  scheme has OTA, so nothing changes there.
- NVS (0x9000, 20 KB), otadata and the core dump area stay at the same offsets. The app partition
  grows from 0x200000 to 0x300000 bytes and the SPIFFS partition shrinks from 1,966,080 B (1.9 MB)
  to 917,504 B (896 KB) at 0x310000. The firmware does not use SPIFFS.
- The released image is still one 4 MB merged image written at 0x0, so the web flasher writes it
  the same way. `meta.json` has `partition_scheme` (`huge_app`), `app_partition_size`
  (`3145728`) and `static_ram` / `static_ram_max` (global variables and their limit, bytes), and
  its `fqbn` ends in `PartitionScheme=huge_app`.
- Stored settings are not carried over from 2.3 anyway (see above); the new layout does not change
  that.
- **Tools:** the `[build] partition_scheme` key needs xewe-os-tools 3.1.0 or later (3.1 pins
  3.1.0). Tools 3.0.x stop with `xewe.toml: unknown key(s): build`.

## LED

- **Rendering runs in its own FreeRTOS task** (every 20 ms) instead of `loop()`. Frames are the
  same as 2.3.0. The strip keeps animating while the console waits for an answer, including the
  first-boot waits of HomeKit, Alexa and Home Assistant.
- **`$led reset` also clears the mode parameters.** In 2.3.0 they lived in a separate `mc`
  namespace and survived a reset; now they are part of the `led` namespace.
- **Wizard:** a "no" to a pin question prints how to change the pins and the setup continues (2.3.0
  hung there forever). With wrong pins the colour-order calibration shows nothing; answering
  "Other" restarts into the wizard.
- **`$led status`** prints `Led module enabled` first, then one line per setting, then the
  hardware, live state and mode lines.
- Corrected 2.3.0 bugs: Color Fade Two Zone reports a defined colour; LEDs past the configured
  length stay dark; the parallel-lines setup saves the LED count; `adj_mode_param` with an unknown
  key does nothing; a missing stored colour or an out-of-range stored chip/colour order falls back
  to the defaults.
- Kept on purpose (stored commands rely on them): an unknown mode id runs mode 0 but is stored;
  `set_hsv` with V=0 gives white; at boot mode 0 takes the colour of the last active mode.
- Pins are fixed at build time (`XEWE_MODULE_LED_PIN_DATA` / `_CLOCK`); the default is the Led
  Dock V2 pair (c3 4/3, c6 20/19, s3 13/12).

### Fixed in led 3.1.0

Command names, arguments and response texts are unchanged, so stored button and schedule
commands keep working.

- **Colour-order calibration on an already calibrated strip finds the right order**
  (`$led set_color_order ""`). The test colours are now shown in plain RGB order before the
  questions. 2.3.0 showed them through the order already applied, so re-calibrating a GRB strip
  with truthful answers stored RGB. Behaviour change from 2.3.0; a first calibration is unchanged.
- **Colour-derived mode parameters stay inside the mode's range.** `set_rgb` and `set_hsv` clamp
  the hue/saturation they store to the mode's declared range, as `set_mode_param` does. Color
  Fade's Min Saturation (0..245) now stops at 245, where 2.3.0 stored 246 after `set_mode 1` and
  255 after `$led set_rgb 255 0 0`. This changes Color Fade's frames for such colours. Values
  already stored are not clamped when loaded (as before). Behaviour change from 2.3.0.
- **`$led set voltage` refuses a value other than 5, 12 or 24 before storing it**: it prints only
  `! Led: voltage must be 5, 12 or 24; kept <v>` and writes nothing. 2.3.0 had no `$led set`
  (voltage came from the wizard menu only); the 3.0 development builds printed `voltage=<v>`
  first and wrote NVS twice. A valid value prints `voltage=<v>`.

## LED web page

- **Colours are parsed strictly.** `/set?color=` accepts six hex digits with an optional `#`;
  anything else is refused with `400 Invalid color` and nothing changes (2.3.0 did not check the
  input). `#RRGGBB` now gives that colour (2.3.0 gave black).
- Led Web takes `/` for the LED page; the web-interface `root` setting has no effect while Led Web
  is enabled.
- `$led_web status`: `Led Web module enabled`, then Page, WebSocket Port and WebSocket Clients.
  The 2.3.0 uptime and memory lines are now in `$web_interface status`.
- **Port 80 is required** for Alexa (SSDP and description.xml advertise :80) and for Home Assistant
  discovery (the mDNS service advertises port 80 and the printed `/provision` URL has no port).
  Keep the web-interface `port` setting at 80 when you use them.

## Schedule page

- The schedule page is its own module (`Schedule Page`). It has no `$` command group and cannot be
  disabled; `$system status` shows it `Yes` whenever Led Web is
  enabled. It **requires Led Web** (the page links back to `/`), not the scheduler. Its six files
  are byte-identical to 2.3.0, on the same paths.
- **While Led Web is disabled, every boot prints**

  ```
  Schedule Page module requires:
  Led Web, use: $led_web enable
  ```

  (no `Setup` header) and the schedule routes are not registered, so `/schedule` gets the catch-all
  404. `$led_web disable` lists Schedule Page among its dependents and prints
  `Schedule Page module reset and disabled` although it is neither: it is only not served from the
  next boot on. The page comes back with `$led_web enable`.

## Web server catch-all and web-interface boots

These are web-interface 3.1.0 changes (xewe-os-modules); this product has no catch-all module
of its own any more.

- **Catch-all:** the web interface installs the 2.3.0 catch-all on every boot where it runs: CORS
  headers, `OPTIONS` → 204 (empty), any other unmatched request → `404 text/plain` `404: Not Found`.
  When Alexa is enabled it replaces the catch-all with its own handler, as in 2.3.0.
- **Server on every boot:** the web interface starts its HTTP server on every boot, including its
  setup boot (a fresh device, or the boot right after `$web_interface reset`), as in 2.3.0. It
  prints `Web Interface now available at:` and the URL on every boot, the setup boot included
  (2.3.0 printed a different text, on regular boots only). The LED page, the schedule page and
  Home Assistant's `/provision` and `/deprovision` answer on that boot too. Web-interface 3.0 had
  no server on that boot.
- **The product's fallback module is removed.** The 3.0 development builds of this product had a
  separate `Web Fallback` module (`src/WebFallback/`) that installed the catch-all; 3.1 removes it,
  and `$system status` has no row for it.
- Home Assistant no longer starts the HTTP server itself on its first-boot wait; the web interface
  has already started it.

## HomeKit

- **`$homekit reset` forgets the HomeKit pairings only** (HomeSpan `U`). In 2.3.0 it sent `F`,
  which also erased HomeSpan's Wi-Fi data and stored characteristic values. The same applies to
  `$homekit disable`, the `x` abort of the pairing wait and `$system reset` (which then erases the
  whole NVS, HomeSpan's data included).
- While HomeKit is disabled (HomeSpan not started on this boot), `$homekit reset` and
  `$system reset` erase only the stored pairing list. 2.3.0 sent `F` there; HomeSpan's `U` cannot
  run before HomeSpan has started.
- After a reset, remove the accessory from the Home app and pair again with code `4663-7726`.
- The pairing code is unchanged (`4663-7726`). The printed QR link now points to
  `https://github.com/xewe-labs/xewe-led-os/raw/main/static/media/HomeKit_Connect_QR.png`, the same
  image, now kept at `static/media/HomeKit_Connect_QR.png` on main (set `HOMEKIT_QR_URL` to change
  it).

## Home Assistant

- mDNS TXT `fw` and the discovery `sw_version` carry the real firmware version (2.3.0 always said
  `0.4.0`). Everything else (topics, ids, payloads, `/provision`, `/deprovision`) is 2.3.0.
- `wifi` is a direct requirement (`$wifi disable` disables Home Assistant too). The web interface
  cannot be disabled since 3.0, so the requirement through it would no longer reach this module.
- The LED keeps animating during the first-boot wait (the led renders in its own task).
- On the boot right after `$web_interface reset`, `/provision` and `/deprovision` answer
  (web-interface 3.1.0 starts the server on its setup boot).
- The module id stays `homeassistant`, its name `Home_Assistant`.

## Every module (XeWeCore 3.1)

- **Every restart prints a `Rebooting` header and waits 1 s** (2.3.0 restarted silently),
  including the restart after the serial `x` abort of the HomeKit, Alexa and Home Assistant waits,
  `$<module> enable|disable|reset` and the `$wifi disable` cascade.
- `$<module> enable` prints `<Name> module enabled` (no "Restarting..."); `already enabled` is
  printed only in verbose mode.
- **The disable confirmation times out**: two attempts of 15 s; no clear "yes" cancels the
  disable. 2.3.0 waited forever.
- **Modules with a settings table gain `$<id> set|get|schema`** (for example `$led`). HomeKit,
  Alexa and Home Assistant have no settings table, so the core does not add these three commands
  to them: `$homekit`, `$alexa` and `$homeassistant` keep exactly the 2.3.0 commands (status,
  reset, enable, disable), and `$homekit set` answers
  `Error: Unknown command 'set' in command group 'homekit'`.
- `$system status` has one new row: Schedule Page. `$system reset` prints its extra reset line.
- Modules loop in declaration order (2.3.0 looped them alphabetically).

## First-boot order

The order of prompts and waits changed, because the generated module list begins time, scheduler
and buttons before the product's modules:

| | 2.3.0 | 3.1 |
|---|---|---|
| 1 | device name | device name |
| 2 | LED wizard | LED wizard |
| 3 | Wi-Fi | Wi-Fi |
| 4 | web interface | web interface, Led Web |
| 5 | Home Assistant (wait) | time zone |
| 6 | HomeKit (wait) | scheduler |
| 7 | Alexa (wait) | buttons |
| 8 | time zone | Home Assistant (wait) |
| 9 | scheduler | HomeKit (wait) |
| 10 | buttons | Alexa (wait) |

The three smart-home waits block without a timeout, as in 2.3.0; type `x` to skip one.
`xewe provision` answers the name, Wi-Fi and time-zone prompts only. It cannot answer the LED
wizard menus or the smart-home waits; answer them on the console.
