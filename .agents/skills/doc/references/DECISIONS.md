# Decisions

Each line records one decision that a later change could undo by accident. Write it as a date,
the decision, and the reason, with the newest line last.

D7 is unused. The dates of D1 to D24 are the commits that first contained the id (git log -S), so the real decision may be older.

2026-10-08 D1 Target hardware is ESP32-C3, -C6 and -S3 only, because the library metadata names these three.
2026-10-08 D2 No OTA, because the partitions stay `no_ota` and flashing is serial only.
2026-10-08 D3 Template use is `git clone`, `./setup.sh`, `./run.sh`, because `setup.sh` writes `run.sh` and needs only Python and git.
2026-10-08 D4 All modules live in one repo, `xewe-os-modules`, so there is one contract, one validator and one index.
2026-10-08 D5 Stay on arduino-cli, because PlatformIO is not clearly better: its espressif32 platform still ships Arduino 2.0.17 (Arduino 3.x on C6 needs the pioarduino fork), it has no lock file, and the test runner is custom code either way.
2026-10-08 D6 Tests run against an attached board and compile only without one, and both paths are first class.
2026-10-08 D8 There is one library, `XeWeCore`, so the `xewe-os` and `XeWeOS` names cannot collide. ArduinoJson is its only dependency.
2026-10-08 D9 It is called "Core" and not "Kernel", because a kernel implies scheduling and memory management, which this does not do.
2026-10-08 D10 One tooling repo, `xewe-os-tools`, holds setup, build, flash, serial and test, so port discovery and serial code are shared.
2026-10-08 D11 The template gets its dependencies through `setup.sh` and `xewe.toml`, one ref each, and nothing generated is committed. There are no submodules.
2026-10-08 D12 The core is semver and published, each module declares `requires_core`, and the template pins both in `xewe.toml` with a version of its own (see VERSIONING.md).
2026-10-08 D13 The module contract keeps the explicit `declare` line in `module.properties`, because a validator can check it and a constructor parser in the tools would hide the wiring (see MODULE_CONTRACT.md).
2026-10-08 D14 Tests are Python driven from the host, in `tests/board/` and `tests/unit/` only, and there are no on-device Unity tests.
2026-10-08 D15 One board is attached at a time and a build costs about a minute per chip, so `build` and `test` compile only the selected chip unless `--all-chips` is given.
2026-10-08 D16 Utils is inside `XeWeCore`, because it is header-only and everything depends on it.
2026-10-08 D17 `XeWeCore` is an `XeWeOs` facade plus standalone component headers (see CORE.md).
2026-10-08 D18 There is no separate publishing tool. `XeWeCore` is released by its own `scripts/release.sh` and its CI runs `arduino-lint` strict, because one library is left to publish.
2026-10-08 D19 Repo names carry the prefix: `xewe-os-core`, `xewe-os-modules`, `xewe-os-tools`, `xewe-os`, so they read as one project.
2026-10-08 D20 `xewe-os` is a GitHub template repository and stays plain-cloneable, because "Use this template" gives fresh history and a clone keeps working.
2026-10-08 D21 Modules are built and tested through a `xewe-os` checkout as the harness, so the modules repo carries no toolchain and there is one build path that cannot drift.
2026-10-08 D22 No board is a normal state. Board tests compile only, the runner prints `compiled, not run` and exits 0, and `--require-board` makes it an error (see NO_BOARD.md).
2026-10-08 D23 Coding agents do the hands-on work and a supervising session verifies and steers, so issues are resolved and logged and only critical ones interrupt the maintainer.
2026-10-09 D24 Refs were `latest` and harnesses built from local working trees (`XEWE_*_SOURCE`) until every repo was tagged 3.0.0 together. Refs are pinned to tags since.
2026-10-10 D25 Every repo has one layout: `README.md` and `LICENSE.txt` are the only reader files at the root, pages live in `doc/`, the C++ style ships inside the tools, and `.clang-format` and `run.sh` are never committed.
2026-10-14 D26 Binaries are GitHub Release assets and are never committed, so the tag is the source and the Release is the binary. The CI lint `No committed firmware` fails on any tracked file under `static/`.
2026-10-14 D27 Every release has a `release_card.md` generated by `scripts/release.sh` from one run, never hand-written, because it records what ran on which commit and what was not covered. It is part of the tag message and a release asset, and CI fails on a mismatch with the tagged tree.
2026-10-14 D28 A project-local module in `src/<Name>/` is first class: same `xewe::Module` API, contract, tests and NVS rules as a repo module, declared in the sketch, with its values in its own `Config.h` prefixed `XEWE_<ID>_`. It moves to the modules repo (D4) when another firmware needs it.
